## 0. 为什么要有这份规范

注释是本工程唯一**没有机器兜底**的产物：编译门只认 error（`dotnet build Assembly-CSharp.csproj`），
测试只有 `Assets/Tests/Runtime/Editor/` 下几个 EditMode 用例（见 `AGENTS.md` §9），覆盖不到手感和观感。

更麻烦的是本工程是**单程序集**：`Presentation ➔ Logic ➔ Data ➔ Foundation` 四层只靠命名空间自觉
（`AGENTS.md` §2）。边界、时序、单位、真假语义这些"错了既不报错也不崩、只表现为手感错"的东西，
**唯一能落字的地方就是注释**。于是它们必然要写，也必然会被顺手写多。

所以本规范的重点**不是教怎么写注释，而是设一条能自动拦住的预算线**：`pwsh Tools/comment-lint.ps1`。
判据覆盖 `Assets/Scripts/**` 的手写 C#；生成物、`Library/`、`Temp/`、`obj/` 不在内。

## 1. 唯一判据（每次想写注释，先问这一句）

> 这条注释是不是在防止某个人做出一个「**编译门不拦、没有测试会红、只表现为手感 / 观感 / 性能错**」的改动？

- **是** → 写，并且压成**一行**。
- **否** → 不写。

写不出"删了会有人做错的具体场景"，就是不该写的注释。

四条硬禁令：

- **死代码不许注释着留**：注释掉一段实现等于把它变成一份不会编译、不会报错、还会误导人的副本。
  本轮清掉的实例：`ResMgr` 三处（`//MonoMgr.Instance.StopCoroutine` / `//resDic.Remove(resName)` / `//resInfo.isDel = true`）、
  `BasePanel` 的两行（`//root.UIMgr.RigisterPanel(this);` / `//root.UIMgr.UnRigisterPanel(this);`）、`ResMgr.LoadAsync` 末尾的 `//MonoMgr.Instance.StartCoroutine(...)`。
- **进度叙事不进代码**：`TODO` / `待办` / `将来会做` 写到 `Docs/` 下对应的需求或说明文档，或写进提交说明。
- **装饰性分隔横线不许有**（生成物自带的除外）。
- **不许按字数机械裁剪**：删法只能是逐条判断它在不在 §2 那 9 类里。

## 4. 形式硬规则

1. **XML 标签白名单只有 `<summary>` 和 `<remarks>`。**
   出现以下任何一个都算违规，必须**物理删掉标签本身、保留其中的文字**：
   `<c>` `<para>` `<b>` `<i>` `<em>` `<strong>` `<paramref>` `<param>` `<returns>` `<list>` `<item>` `<code>` `<br>` `<p>` `<see cref>` `<seealso>` `<inheritdoc>` `<example>` `<exception>` `<value>`
   - `<see cref="Foo"/>` → 写成纯文本 `Foo`（`MoveGroup` 里的 `<see cref="EmptyTag"/>` 已降级成 `EmptyTag`）。
   - 泛型写法 `<see cref="Pool{T}"/>` → 写成 `Pool`（别留下 `<T>`，它会被判成标签）。
   - **XML 转义只在"标签已被删掉"之后才还原**：`&lt;` `&gt;` `&amp;` → `<` `>` `&`。
     仍留在 `<summary>` / `<remarks>` **内部**的转义必须原样保留（例：`<summary>Duration 秒且 &lt;=0 表示永久</summary>`），
     改成裸 `<` 会让 `///` 注释的 XML 非法。
2. **注释以单行为常态**：`<summary>` / `<remarks>` 允许跨行，但必须在**同一个连续注释块内开闭配平**
   （块与块之间由非注释行分隔）；块结束时仍未闭合就是违规。推荐压成一行：
   ```csharp
   /// <summary>子类自己设置文本字体，默认为正文</summary>
   ```
   允许的跨行形态（标签独占一行、块内配平）：
   ```csharp
   /// <summary>
   /// 子类自己设置文本字体，默认为正文
   /// </summary>
   ```
   相邻的 `/// <summary>…</summary>` 与 `/// <remarks>…</remarks>` 是**两条**独立注释，合法。
3. 标签内不留首尾空格：`/// <summary> 检查是否能抢占 </summary>` → `/// <summary>检查是否能抢占</summary>`；
   不写空标签（`<returns></returns>`、`<param name="x"></param>` 整行删）。
4. 删掉整行注释后，**连续空行收敛到最多 1 行**。
5. `#region` 只许在 150 行以上的装配类 / MonoBehaviour 里做**名词短语**分组（`#region 物理检测`），单文件 ≤4 组、不嵌套。
   不许把 region 当注释用，也不许拿它当分区装饰。当前上限样式：`MoveMotor.cs` 3 组、`BasePanel.cs` 1 组。
6. 中文保持中文，不中英混排同一句；一条注释只写一句话，不用感叹号。
7. **改注释时不许动代码**：不合并 / 不拆分行、不改缩进、不改标识符、不改字符串字面量
   （`[Tooltip("…")]`、`[Header("…")]`、`[SerializeField]` 后面的中文串**是代码**）。
8. **Inspector 文案（`[Tooltip]` / `[Header]`）单独一套规则**——本仓 59 条 Tooltip、11 条 Header，是比注释更大的文档面：
   - 新增或修改任何可调字段，必须带 `Tooltip`；纯功能性引用字段带一句"由谁赋值"。
   - `Tooltip` 必须写**单位**（秒 / 米 / 单位每秒 / 单位每秒² / 倍率 / 层）**和边界**（0 表示什么、负值算什么）。
   - 反直觉后果必须写进去：`enableGravity` 那条「开启时请把刚体 Gravity Scale 设为 0，否则两套重力会叠加」是标杆。
   - 首行写"是什么"，细节用 `\n` 换行另起；不让第一行被 Inspector 宽度截断。
   - **不许与字段名重复**（`[Tooltip("移动速度")] public float moveSpeed` 等于没写）。
   - `Tooltip` 说过的，字段上不再写 `<summary>` 复述一遍。
   - `Tooltip` 属于代码，**不计入注释预算**；但改动它和生产代码一样要过编译门。
9. **注释与文档分工**：帧序、状态图、规则清单写进 `Docs/说明/玩家状态机.md`；代码里只留一句"为什么错"。
   只有 `PlayerLogic` / `MoveGroup` / `PostureGroup` / `MoveMotor` 四个类允许在类头指向该文档，
   其余文件不许写"详见某文档"——那只是把读者踢走。

## 5. 预算与守卫（机器判据）

### 5.1 口径

**注释有效字符数**：逐行取注释正文，剔除 `//`、`///`、`/*`、`*/` 标记本身与换行符；
**标记之后的空格、行尾空格、块注释续行的缩进都计入**（`// 文本` 比 `//文本` 多算 1 个字符）；
其余（文字 / 标点 / 空格 / XML 标签）全部计入。字符串字面量里的 `//` 不算注释。

`[Tooltip("…")]` / `[Header("…")]` 里的中文**是代码**，不进这个口径（它们的规矩见 §4.8）。

两个推论：① 删掉一整个 `/// <summary></summary>` 行比改写它更省，光标签壳就值 19 个字符；
② 按密度看，**文档注释特别密的接口/工具类天然吃亏**，所以它们按文件单独登记（§9）。

规则：

- **只降不升**：动过的文件，注释字符数不得超过上表现值；压下来多少算多少，但本轮不许涨。
  实测差额 = `pwsh Tools/comment-lint.ps1 -Mode report`。
- **新文件**：额度 = `max(8.0 × 代码行, 250)`。8.0 是**首次封印时**全仓密度 6.22 之上留的余量，
  不随清理结果下调（否则越清理，新文件越难写）；250 是给短文件的保护地板（十几行的接口按密度只算出百来个字符，写两句契约就超了）。
  超额度说明在替代码解释，不是在防坑；接口 / 枚举类新文件可单独登记，登记动作就是 `-Mode seal`。
- **容差**：`上限 < 实测 ≤ 上限 + 容差` 只报 WARN 不阻断（容差 = clamp(预算/2, 20, 50)），
  吸收"合并上游带进来的一行注释"这类噪声；超容差才算违规。

### 5.3 命令

```bash
pwsh Tools/comment-lint.ps1                      # 全量判定：预算 + 标签，违规 exit 1
pwsh Tools/comment-lint.ps1 -Mode report -Top 30 # 逐文件 预算/现值/余量/密度 表（按超支排序）
pwsh Tools/comment-lint.ps1 -Mode tags           # 只查 XML 标签白名单（含存量对比）
pwsh Tools/comment-lint.ps1 -Mode verify -Base <rev>   # 证明"只改了注释、代码零改动"
pwsh Tools/comment-lint.ps1 -Mode check -StagedOnly    # 只看本次改动的 .cs（提交前）
pwsh Tools/comment-lint.ps1 -Mode seal           # 清理验收后重新封印预算（会 diff 出预算变化）

pwsh Tools/compile-gate.ps1                      # 编译门：0 error + 警告不超基线 + 无越层/驱动违规
pwsh Tools/compile-gate.ps1 -Seal                # 修好存量偏差后重新封印警告与守卫基线
```

`compile-gate` 现场重扫 `Assets/**/*.cs` 生成临时工程（`Temp/compile-gate/`），
所以**新加的文件不会因为 csproj 清单过期而被漏编**；它同时补上编译器拦不住的两条：
越层 `using`（`Foundation`/`Data`/`Logic` 不许指向上层）与"只有 `GameRoot` 能写 `Update`/`FixedUpdate`"。
存量偏差（当前 1 处越层 + 2 条 `CS0649`：`StateMachine.cs` 的 `using Refraction.Logic`、
`GameRoot._uiMgr` 与 `_resMgr`）登记在 `Tools/compile-gate.json`，只减不增。

### 5.4 什么时候允许上调预算

只有一种情况：**这个文件确实承担了新复杂度**（新增了一整块子系统，不是"顺手写详细点"）。
做法：`-Mode seal` 后把理由写进 `comment-budget.json` 的 `budgetRaises`（该字段就是给 review 看的），
并在提交说明里点明"哪几行 / 挡的是什么坑"。
日常开发、加功能、写新类，都不许把超标的现值当新基线——那正是本规范要防的事。

## 6. Definition of Done

动了 `.cs`（哪怕只动注释）就要过这四条：

- [ ] 1. `pwsh Tools/compile-gate.ps1` → `GATE OK`（0 error，警告与基线一致，无新增越层 / 驱动违规）
- [ ] 2. `pwsh Tools/comment-lint.ps1` → `LINT OK`（预算不超，无新增白名单外标签）
- [ ] 3. 改了注释时：`pwsh Tools/comment-lint.ps1 -Mode verify -Base <上一个已验收提交>` → `VERIFY PASS`
- [ ] 4. 没碰 `Generated/InputSys.cs`、`Library/`、`Temp/`、`obj/`、`*.csproj`；
      没有顺手改代码 token、缩进、EOL、BOM；没有手改 `Tools/*.json`（只许 `-Seal` / `-Mode seal` 写）

## 7. 反例对照（本仓真实片段）

### 7.1 复述命名 → 整组删（已落地）

```csharp
// ✗ 前（UIMgr.ShowPanel，三行注释零信息）
if (panelDic.ContainsKey(panelName))
{
    //取出字典中已经占好位置的数据
    PanelInfo<T> panelInfo = panelDic[panelName] as PanelInfo<T>;
    //正在异步加载中
    if (panelInfo.panel == null)
    {
        //如果之前显示了又隐藏 现在又想显示 那么直接设为false
        panelInfo.isHide = false;

// ✓ 后：只留"为什么"
if (panelDic.ContainsKey(panelName))
{
    PanelInfo<T> panelInfo = panelDic[panelName] as PanelInfo<T>;
    if (panelInfo.panel == null)
    {
        // 异步没落地就被 Hide：置回 false，回调攒在记录上等落地统一补发
        panelInfo.isHide = false;
```

`//取出字典中…` 只是把 `as PanelInfo<T>` 念了一遍；`isHide = false` 那行才有信息（谁补发回调）。

### 7.2 长段设计论证 → 压成一行结论（已落地）


## 9. 常见问题

**Q：接口文件、纯枚举文件密度天生很高，也要压吗？**
A：不。`IMoveMotor` / `IDoorReader` / `ISceneRoot` 这类接口是**跨层契约的唯一落点**
（`AGENTS.md` §4.4「接口防腐」）——返回 `false` 的语义、谁负责调用、调用时机，只有这里能写。
`IDoorReader` 密度 36.6、`IMoveMotor` 10.1 都高于 8.0 的新文件线，它们照样合规：
问题不是"密度高"，而是"有没有 §2 那 9 类信息"。新接口文件同理，按文件登记即可。

**Q：生成物里的注释要清吗？**
A：不要。`Generated/InputSys.cs` 由 Input System 覆盖（`AGENTS.md` §3）。要改键位去改
`Presentation/Input/InputSys.inputactions`，别在产物上动手。它的头注释里还写着旧路径
`Presentaion/Input/…`，下次生成时会自动更新，不用手动改。

**Q：现在还有没有白名单外标签的存量豁免？**
A：没有了。2026-11-06 全仓清理后现存 0 处（清理前 53 → 46 → 0），`comment-budget.json` 的 `tagAllow`
已是空表，所以此后**任何** `<see cref>` / `<param>` / `<paramref>` / `<typeparam>` / `<returns>` / `<c>`
都是直接 FAIL，不再有"只要求不新增"的缓冲。`-Mode tags` 报的就是硬违规，不是历史包袱。

**Q：清理完了，预算会不会一直这么低？**
A：会按"只降不升"钉住。以后每个文件的额度就是 §5.2 这张表的现值，想涨只能走 §5.4
（写进 `budgetRaises` 并在提交说明里点明"哪几行 / 挡的是什么坑"）。这是有意的：
清理省下来的余量不是给下次写长注释用的。

**Q：我给 `[Tooltip]` 写了 5 行，算不算超预算？**
A：不算。它不进注释预算，但受 §4.8 约束——单位、边界、反直觉后果必须有，纯复述字段名不行。

**Q：我做功能时顺手加了 5 行注释，预算报超了，但我确实需要它怎么办？**
A：先按 §1 判据逐条删一遍——十有八九能压回去。真的压不回去，说明这个文件承担了新的复杂度，
在提交说明里写明理由并按 §5.4 上调，让它被 review 看见。

**Q：`<summary>` 能不能拆成两行？**
A：能，但要在同一个连续注释块内开闭配平（§4.2）。跨行不省字符、反而更占预算，
所以默认仍是一行写完；一行写不下通常说明该删的东西还没删干净。

**Q：`Debug.Log(_currentState.Tag.ToString())` 这种调试输出算注释问题吗？**
A：不算注释，但属于 §2 第 8 类该管的"信噪比"：每次切状态都往 Console 打一行，交付后既是噪音，
又会把真正的错误盖掉。`StateMachine.cs:55` 是现存的一处，谁动这个文件谁顺手清掉
（删掉，或只在 `#if UNITY_EDITOR` 下保留）。
